# Settings and questionnaire UI - what the evidence supports

This is the reference used to judge candidate designs for the `copier-tui` questionnaire screen: 23 questions, most single-choice from 2-5 options, several conditional, all pre-filled with a computed default that is usually right, in a 100x32 keyboard-only terminal. It states which received wisdom survives contact with its primary sources, what the surviving evidence obliges the design to do, and where a designer is on their own.

## What holds up, and what does not

| Claim | Verdict | Consequence for this design |
|---|---|---|
| More visible options increase burden, so hide alternatives until requested | folklore | Stop optimising hidden-vs-visible; the paying variable is aligned-vs-unaligned columns |
| A pre-filled default reduces burden | contested (both halves measured, the trade never measured) | Keep all 23 prefilled, and spend the screen on making each one cheap to verify |
| A pre-filled default becomes an invisible non-decision | contested (same body of evidence) | Three provenance states and a count line; friction and nagging do not fix it |
| Five named sections beat one flat list of 23 at equal visibility | folklore (the experiment has never been run; the naming half has a direct null) | No section headings; group with a blank line, by dependency, if at all |
| A delta summary ("3 changed, 20 defaults") comprehends faster than the full list | contested (true for relation tasks, refuted for value retrieval) | Count line as an addition, never a substitute for the 23 rows |
| Limit a list to 7 plus or minus 2 | folklore | 23 visible rows is not a memory violation; only the row budget constrains it |
| Hick's law proves fewer options are faster | folklore | Never truncate an option list for speed; 2 to 5 options is about 1.3 bits |
| Too many choices paralyse (paradox of choice) | folklore unconditionally, conditional at best | Do not cut a 5-option question to 3; the live moderator is preference uncertainty |
| Users suffer decision fatigue over a long form | folklore | No rest prompts, no session splitting; satisficing is the real failure mode |
| Reduce cognitive load by showing less | folklore as stated | Load tracks element interactivity, not element count; the coupled rows are the cost |
| Progressive disclosure reduces load | unresolved (craft heuristic, no controlled evidence) | Use it for per-question detail only, never for the 23 current values |
| Dropdowns cause about 25% more errors | folklore (untraceable) | Do not cite it; decide dropdown-vs-inline on occlusion and column width |
| Fewer than 5% of users ever change a setting | folklore (self-selected email sample) | Cite Mackay 1991 if you need the point at all |
| Progress indicators reduce abandonment | folklore (meta-analysis null, and worse when slow-to-fast) | Ship no progress bar; a count of rows owing a decision if anything |
| Grids cause straightlining, so never build a dense table | supported but does not transfer | The mechanism needs one shared response scale; 23 heterogeneous rows have none |
| Defaults determine what gets recorded | supported (d = 0.68, N = 73,675) | Whatever the defaults say is what ships; the confirm screen is the obligation that follows |
| Search rescues a badly shaped menu | folklore | Fix the list; search does not beat browsing even at e-commerce scale |
| Hiding navigation is a fair trade for space | supported against (over 20% discoverability loss, 39% slower) | Nothing that is state may live behind a reveal |
| Removing one form field earned Expedia twelve million dollars | folklore (corporate anecdote, no method) | The instructive part is only that an ambiguous label costs more than a missing feature |
| The data-ink ratio is empirically validated | contested (direct tests mixed to negative) | Argue restraint from the cell budget, which is checkable, not from Tufte |

Sources for the four adjudicated rows, in order: Scheibehenne, Greifeneder & Todd 2010 (63 conditions, N = 5,036, D = 0.02, CI95 -0.09 to 0.12) with Chernev, Bockenholt & Goodman 2015's own no-moderator model agreeing (t(20) = -.10, p = .48), against which no study in the choice-overload literature ever manipulated visibility - every arm showed every option; Engstrom & Sinibaldi 2024 (JSSAM 12(1):60) for burden reduction against Madrian & Shea 2001 and Eggs & Jackle 2015 for the unread configuration; Smyth, Dillman, Christian & Stern 2006 (headings isolated from spacing: 64.6% vs 66.8%, chi-square 0.38, p = .538) and Mogilner, Rudnick & Iyengar 2008 (no main effect of category count, F(1,57) = 1.72, NS) for the sections claim; Srinivasan, Brehmer, Lee & Drucker CHI 2018 (delta-only design could not perform half the task families; 40.5% of 74 participants named it worst) against Nothelfer & Franconeri 2019 (25-95% improvement, but every task was a relation task) for the delta claim.

## Rules

### The budget every rule spends from

At 100x32: seven rows of chrome - header, rule, two to three detail-band rows, rule, footer - leave 25 rows for 23 questions, two spare. Across 100 columns, 2 status + 22 label + 20 value + separators is 45 used and 55 free. Those 55 fit `3.11 3.12 3.13 3.14` at 22 columns and do not fit `MIT Apache-2.0 BSD-3-Clause GPL-3.0` at about 40 once a dependency note shares the line, which is why "all alternatives on every row" cannot be the rule.

At 80x24 the same chrome leaves 17 rows against 23 questions, six short, and 35 free columns, which kills the alternatives column at any width. Degrade in this order: alternatives first, the origin column second, the question id third, then collapse runs of untouched defaults into one counted line that expands with a key. Never degrade by hiding values, by dropping the provenance mark, or by turning the list into a wizard - the evidence that hiding state is costly does not weaken when the terminal shrinks.

### Presenting the question

- **Show all 23 rows at once; never paginate to reduce load** (Sweller 2010 - load tracks element interactivity, and 23 independent single-choice questions have interactivity of about 1 each; Pernice & Budiu 2016 measured the cost of the alternative) - cost: 23 of 25 usable rows
- **Reserve a fixed-height detail band at the bottom for the focused row; never expand inline** (Cockburn, Gutwin & Greenberg CHI 2007 - the novice-linear to expert-logarithmic shift happens only under stable item placement, which inline expansion destroys) - cost: 3 rows permanently, 9% of the screen
- **Put one line of consequence text on the focused row** (Chernev 2015 - preference uncertainty is the live moderator at .32; Dean, Ravindran & Stoye 2022 - when each option is expensive to evaluate, three options already push people onto the default) - cost: one band row, and the template author must write 23 sentences
- **Give a key that suppresses help globally, and do not make it adaptive** (Kalyuga, Ayres, Chandler & Sweller 2003 expertise reversal; Findlater & McGrenere CHI 2004 - the static menu was significantly faster than the adaptive one) - cost: one binding, one persisted boolean
- **Do not spend rows on section headings** (Smyth et al. 2006 - headings isolated from spacing were null at chi-square 0.38, p = .538, while spacing carried the whole effect at 40.9% to 70.2%; and five heading rows overflow the budget above) - cost: none, it returns five rows
- **Keep `copier.yml` declaration order; never sort by frequency, recency or alphabet** (Cockburn et al. 2007 stable placement; declaration order is the causal order because `when` conditions and Jinja defaults reference earlier answers) - cost: a user hunting a known name cannot binary-search
- **Do not build a wizard** (Budiu NN/g 2017 - wizards are contraindicated for repeat users, for many-field entry, and for tasks needing cross-step comparison, which is three of five exclusions and the third is goal 2 by definition) - cost: you inherit the error and branching problems one-question-per-page was invented to dodge
- **Do not delete a question or trim a 5-option list to reduce load** (Scheibehenne et al. 2010; Liu et al. CHI 2020 - 2 to 5 options is about 1.3 bits, roughly 100 ms, less than a repaint) - cost: none

### Presenting the options and the ones passed over

- **Show the full alternative set for the focused row only, and justify it by column arithmetic, not by cognitive load** (the licence row does not fit in 55 columns; Liu et al. CHI 2020's second design principle - already-categorised items should be split, and 80 option tokens are categorised by question) - cost: an honest design doc that does not claim a load benefit it cannot support
- **Put a count suffix on every unfocused row: `MIT  +3`** (Baymard - 55% of users open a drop-down purely to see what is inside, so the wondering happens whether or not you answer it) - cost: 4 columns, 92 cells, 2.9% of the screen
- **Cycle 2-5 options in place in the value cell; reserve an overlay for genuinely long lists** (alsamixer edits enumerations in place with no popup; btop's `◄ value ►` with a `2/4` position; a Textual `Select` overlay covers the rows beneath it, which are exactly the rows being compared against) - cost: a cycling control teaches itself less readily than an opening list
- **Never render a hidden control with no count** (macOS Ventura's popup buttons appear only on hover, so the control is invisible until pointed at; NN/g's one transferable accordion rule is that a collapsed heading must state its contents) - cost: 4 columns you were trying to save
- **Put the computed default first in the option list** (Galesic, Tourangeau, Couper & Conrad 2008 eye-tracking - on a 12-option question 10% of respondents never fixated the last two options) - cost: the option order stops matching `copier.yml` unless the template already leads with the default
- **Keep exactly one option marked as current at all times, and give focus a visually distinct treatment from selection** (GOV.UK's published Select research lists "confused the focused item with the selected item" as a repeated failure; a terminal has only reverse video, bold and hue to separate them) - cost: two of your scarce attributes are committed before any state marking

### Marking defaults versus decisions

- **Track three states - derived, default-untouched, user-set - and put the enum in `copier_ui`** (Madrian & Shea 2001 - 71% of auto-enrolled participants sat at both defaults, a combination 1% of self-enrolled chose; VS Code's `@modified` conflates differs-from-default with explicitly-set and that conflation is the information wanted here) - cost: one field in the state engine, one glyph, one legend
- **Encode state as a glyph in a fixed column; weight second; hue last and never alone** (Treisman & Gelade 1980 - single-feature search is flat at about 3 ms per item, conjunction search is serial at about 60; Christ 1975 - colour aids search only when the target colour is known in advance; Kconfiglib's forced monochrome style carries availability by weight alone, which is the proof it can be done) - cost: 2 columns permanently
- **Align that column so untouched rows form an unbroken vertical run** (Bennett & Flach 2011 configural displays - when an emergent feature such as a straight edge maps onto the task-relevant state, a deviation becomes a preattentive event rather than a symbol to read) - cost: zero cells; this is the highest-leverage item in the document
- **Do not dim the defaults; make the decisions louder** (NN/g on low-contrast text, and the grey-means-disabled convention; Luguri & Strahilevitz 2021 - rendering content in smaller, less prominent form raised acceptance from 14.8% to 30.1%, so de-emphasis is hiding, not styling) - cost: none, it is cheaper than dimming
- **State provenance as a word, not only as a style: `you`, `default`, `from project_name`** (git `--show-origin` and `--show-scope`; Vim's `Last set from <file> line N`; npm's `; prefix = "/opt/conda" ; overridden by user`) - cost: about 10 columns if always on, zero if it lives on the focused row only
- **Mark never-answered with a text token, not an attribute** (menuconfig suffixes ` (NEW)` to any symbol with no value) - cost: about 6 columns on affected rows only, and no palette token
- **Render a null or fallback default differently from a recommended one, and block generation on it** (McKenzie, Liersch & Finkelstein 2006 - a pre-selected option is read as the choice architect's endorsement; copier's own `--defaults` help says the answers "might be null if not specified"; debconf's `high` priority is defined as "items that don't have a reasonable default") - cost: someone must decide, per question, whether the default is a recommendation
- **Do not pre-fill the edit buffer with the default before the user enters the field** (Sherwin NN/g - users mistake pre-filled hint content for data already supplied and skip the field; copier today passes `default=` straight to questionary, so default and chosen are byte-identical on screen) - cost: one extra state in the input widget
- **Never silently rewrite a value the user chose; mark it and count it** (Rensink, O'Regan & Clark 1997 - without a transient that captures attention, large repeated changes go unnoticed, so a full repaint does not communicate that answering question 4 moved question 17) - cost: you must retain the prior value to describe the change, plus an acknowledge key
- **Hold every deviation from a default to two keystrokes** (Johnson & Goldstein 2003 - opt-out at 82% and forced explicit choice at 79% were statistically indistinguishable when changing cost one click, while the country-level gap of nearly 60 points came from changes that cost forms and phone calls) - cost: the keymap must be designed around this number, not measured against it afterwards
- **Say "recommended" freely; be careful what you preselect** (Luguri & Strahilevitz 2021 - labelling an option "(recommended)" was null at p = 0.39, while preselecting it moved acceptance at p = 0.045) - cost: none
- **Build no escalating friction, time-on-row warning or are-you-sure gate** (Loewenstein, Bryce, Hagmann & Rajpal 2015 - disclosing the default before or after the choice did not eliminate the default effect; Conrad, Couper, Tourangeau & Peytchev 2010 - discouraging progress feedback raised abandonment) - cost: you must accept that the count line is true rather than effective

### Showing overall state at a glance

- **Ship one count line - `7 set by you · 14 defaults never opened · 2 derived` - as an addition to the 23 rows, never a substitute** (Srinivasan et al. CHI 2018 - the absolutes-plus-delta design was preferred by 85.1% of 74 participants and was never the worst, while the delta-only design was structurally unable to answer value-retrieval questions and was named worst by 40.5%; Nothelfer & Franconeri 2019 close with the same recommendation) - cost: one row of 32
- **Name the never-opened defaults in that line, not only the changes** (Akl et al. Cochrane 2011 - delta framing of the same quantity was perceived as larger, SMD 0.41, and more persuasive, SMD 0.66, while comprehension was null at SMD 0.02; a "3 changed" headline makes the 3 feel like the whole story when the 14 are the risk) - cost: about 20 more columns on one line
- **Justify the marker by time, not by accuracy** (Srinivasan et al. - explicit encoding "does not guarantee more accurate difference measurement, but it appears to reduce the time to complete the task") - cost: a weaker claim, honestly stated
- **Keep loud rows under roughly a fifth of the list** (EEMUA 191's alarm-rate guidance transfers as a ratio rather than a rate; Breznitz 1984 and the cry-wolf literature - operators match their response rate to observed alarm reliability) - cost: the "needs attention" glyph must fire on 3-6 rows, which means suppressing it on rows that are merely non-default
- **Cap semantic hues in the list body at three** (Healey & Enns 2012 - preattentive detection degrades sharply as the number of distinct distractor types rises; a fourth hue forces conjunction search) - cost: the remaining palette tokens go to chrome and the detail band
- **Show the legend on first entry, not only in a help pane** (L'Yi, Jo & Seo 2021 - across 127 papers, explicit encoding ranked last on familiarity and last on supporting non-comparison tasks) - cost: one row, once
- **Reuse the same rows, order and glyphs on the confirm screen; do not reformat the summary** (re-reading a known spatial layout is what makes the second pass cheap; GOV.UK's check-answers pattern is the same shape) - cost: the summary cannot be denser than the list
- **Make the confirm screen the guaranteed exposure of provenance** (npm init prints the whole resulting `package.json` and asks "Is this OK?"; clig.dev - confirm before doing anything dangerous; Kalkstein et al. 2022 distinguish the recorded choice from the outcome, and in a scaffolder the recorded choice is the outcome seconds later) - cost: one keypress

### Navigating and finding

- **Do not build a find-search box** (Katz & Byrne 2003 - site search did not yield faster or more accurate performance than browsing, and "providing site search should not be used to compensate for poor menu design"; Furnas, Landauer, Gomez & Dumais 1987 - two people pick the same term for the same thing with probability .11 to .12, so a search-first surface over 23 questions is missed by most users on first guess) - cost: a user who knows a variable name has no jump until the next rule
- **Bind type-to-jump or `/` substring filtering over label, value and state token** (menuconfig's `/` with numbered `(#)` jump keys that return to the results on exit; fzf's space-means-AND is the syntax to copy if you need one) - cost: plain letters are consumed whenever no text field has focus, so every other binding becomes a modifier or punctuation key
- **Never return an empty result set; fall back to the unfiltered list with a one-line banner** (Hearst 2009 - a general rule of search usability is to avoid showing empty results) - cost: one row
- **Ship the state filter - modified-only - on a dedicated key, not as a typed query** (VS Code's `@modified` plus issue #65214, where the same filter was buried in an ellipsis menu and users could not find it; Firefox about:config's "show only modified preferences"; `ansible-config --only-changed`) - cost: one binding, and a visible way back to the full list
- **Do not use fuzzy matching at 23 items** (fzf's own issue #638 - the greedy V1 algorithm is not guaranteed to find the best match, and V2 costs O(nm); at 23 rows substring matching already leaves 0-3 results and is explainable in one sentence) - cost: none, it removes work
- **Keep one persistent footer of context-sensitive keys, ranked so it degrades from the tail** (gitui models three states - absent when unavailable, dimmed when available but not enabled, normal when enabled - with an explicit `order` field; Turbo Vision's `TStatusLine` is the ancestor and Textual's `Footer` renders it from `BINDINGS` for free) - cost: one row permanently, the cheapest discoverability on the board
- **Give every function key a printable alias** (nconfig maps digits 1-9 onto F1-F9; alsamixer maps `?` and `/` onto F1 and F2 "on terminals that can't use function keys like gnome-terminal") - cost: two keys spent per action
- **Do not use first-letter hotkeys** (menuconfig's own readme concedes that pressing a hotkey more than once sequences through all items sharing it; 23 arbitrary template labels guarantee collisions) - cost: none

### Moving backwards

- **Make back uniform, lossless and available from every state** (debconf's readline frontend had to retrofit PageUp and Ctrl-U for "previous question", and the protocol carries an explicit backup capability as result code 30; bolt it on late and it will not be uniform) - cost: the state engine owns history, not the screens
- **Keep the answers to questions that became invisible, and restore them if the condition returns** (the concrete bug: answer Q4, Q9 appears and is answered, change Q4, Q9 hides, change Q4 back - Q9 must return with the user's answer, not the default) - cost: retaining answers for hidden fields, plus a flag for "was this answered while visible"
- **After changing a row from the review screen, return to the review screen rather than continuing forward** (GOV.UK check-answers states this as the rule and their research reversed itself in favour of review pages after testing) - cost: an extra transition for a user making several edits in a row
- **On re-entry, do not re-ask what is already answered, and mark a remembered answer as neither default nor fresh decision** (`make oldconfig` prompts only for symbols with no saved setting; debconf's per-question `seen` flag does the same job; copier's `.copier-answers.yml` is the same mechanism) - cost: a fourth provenance value in the model even if the screen renders only three

### Conditional questions that appear and vanish

- **Keep the row when `when` is false: strip the widget, dim the row, and say why** (nconfig overwrites the first three cells with a literal `XXX` and legends it "cannot be selected. Symbol Info <F2> tells you why"; Turbo Vision dims disabled cluster items rather than removing them; menuconfig's default of hiding is the pattern to reject, and its whole search, jump-key and `Depends on:` apparatus exists to undo it) - cost: the list never shrinks, so you never collect the space hiding would have bought
- **Render the reason in plain words, and render it in `copier_ui`** (kconfig's help block prints `Depends on:` and prints `Visible if:` only when it differs, with a source comment saying the redundant line hurts readability; the TUI must never evaluate a `when`) - cost: a `when` expression to English renderer in the core package
- **Indent a dependent row under its controller, and indent the label only - never the status column** (htop marks dependent options with a literal leading `- ` in the label and nothing else; Niemela & Saarinen 2000 found a grouping search benefit only where the group predicts where the target is, which a dependency grouping does and a topic grouping does not; moving the glyph column turns a single-feature search into a conjunction) - cost: 2 columns of label width
- **Group by dependency, never by invented topic** (Tourangeau, Couper & Conrad 2004 - an unfamiliar item takes its meaning from its neighbours, so an inferred boundary asserts a relationship the template author never wrote, and does so on exactly the questions the user understands least) - cost: the arrangement is fixed by the file, not tunable for looks
- **Do not display the cost of a branch next to the branch decision** (Couper, Tourangeau, Conrad & Zhang - when follow-up items were visible inside the grid, respondents answered to avoid them, reporting 8.45 items against 9.89; Eggs & Jackle 2015 found the same shape, with 64.3% confirming a preload that records proved false) - cost: the user cannot see how long the survey will get
- **Show `12/23 visible · 2 unset`, never a percentage** (the denominator moves as conditionals resolve; Villar, Callegaro & Yang 2013 meta-analysed 32 experiments and found constant-speed progress indicators null at LOR 0.072, p = .365, with slow-to-fast indicators raising dropoff odds 1.56 times) - cost: none
- **Give every question a stable short id that survives a neighbour's disappearance** (raspi-config keeps `S1 S3 S4` when `S2` is absent on non-Pi hosts and renumbers nothing) - cost: 3 columns, first to be cut at 80x24

## Prior art worth stealing

**menuconfig and nconfig** are the closest existing thing to this problem - thousands of symbols, most with correct defaults, in 80x24 - and they are worth reading in full. The row is a three-cell value gutter, then indent, then label, and the gutter's *shape* carries editability while the character inside carries value: `[ ]` and `[*]` for an editable bool, `- -` and `-*-` when another symbol forces it, `< >` `<M>` `<*>` for tristates, `{M}` when a reverse dependency pins it to at least module. A single-choice group collapses to one row with the current answer in parentheses and a `--->` trail. A symbol that has never been answered is suffixed with a literal ` (NEW)`. Between them, bracket shape, inner character and one text token answer availability, value and never-looked-at with no colour at all - the shipped `mono` theme still parses. Help is a generated provenance record: `Symbol`, `Type`, `Prompt`, `Defined at file:line`, `Depends on`, `Selects`, `Selected by`, plus `Visible if` printed only when it differs from `Depends on`, with a source comment explaining that refusal. `/` searches by regex, prints exact matches first, and prefixes each result location with a `(#)` jump key that teleports into the tree and returns to the results on exit. The costs are equally instructive: unmet-dependency symbols are hidden by default, and every piece of that search-and-provenance machinery exists to undo the hiding; help is modal, so you cannot read why a symbol is unavailable while looking at it; and first-letter hotkeys collide, which its own readme concedes. nconfig is the better of the two on both counts - it keeps the row and overwrites three cells with `XXX`, legended "cannot be selected. Symbol Info <F2> tells you why" - and it declares a terminal contract, adapting above 80x25 rather than pretending to work below it.

**Kconfiglib's `menuconfig.py`** adds the one thing both lack: `F` toggles a non-modal help pane that follows the cursor. Its forced `monochrome` style sets `list=` to nothing and `inv-list=bold`, which is a working demonstration that availability can ride on weight alone when colour is gone.

**npm `config ls -l`** solves goal 2 completely in plain monospace: where a default has been shadowed it prints the passed-over value, commented, annotated with the layer that beat it - `; prefix = "/opt/conda" ; overridden by user`. Current value, displaced value and provenance, in one line, with no colour. Its cost is that it is a dump: no focus, no editing, no aggregate.

**VisiData's options sheet** encodes chosen-versus-default with no glyph, weight or hue at all. The `value` column returns only the override and renders empty when there is none, sitting beside a populated `default` column; blank-versus-populated is the marker. It costs a whole column to carry one bit, but it survives every terminal.

**Vim's `:options`** puts the alternative on screen at rest for booleans - `set nopaste    paste` - so the passed-over value needs no interaction. It does not mark non-default at all; provenance is a separate one-at-a-time command, `:verbose set tabstop?` returning `Last set from <file> line N`. Two rows per option is why it cannot scale to 23 questions plus chrome.

**debconf** is the most important non-visual precedent. Its four priorities are defined by whether a reasonable default exists - `low` for trivial items whose defaults work in the vast majority of cases, `high` for "items that don't have a reasonable default" - and only questions at or above the chosen priority are shown, with `dpkg-reconfigure -plow` reopening everything later. It also carries a per-question `seen` flag, which is exactly the bit that separates a confirmed default from an unexamined one. The cost lands directly on this project: `copier.yml` has no priority field, so any ranking is inferred (no default means high, `when`-gated inherits its controller, computed means derived) and will sometimes be wrong.

**Firefox about:config** marks state three ways at once - bold for user-set, a literal Status column reading `user set` or `default`, and a "show only modified preferences" filter - and offers a per-row reset that drops the bold. **VS Code** does the same job with a gutter bar plus the `@modified` filter plus per-setting reset, and contributes two cautions: its `@modified` conflates "differs from the default" with "explicitly set", and issue #65214 records that the filter, when it lived in an ellipsis menu, was undiscoverable.

**terraform plan** contributes the leading symbol column (`+ ~ -`), old-to-new pairs, and the fixed summary line `Plan: X to add, Y to change, Z to destroy`; `apt` converges on the same summary shape. Its documented failure is the one to design against: provider-applied defaults and value normalisation produce diffs that are not user changes, and reviewers stop reading a noisy plan.

**htop's setup screen** proves a label can be its own help - options document their own enumerations inline - and marks dependent options with a literal leading `- ` while leaving them always visible and always editable. Its cost is 70-character labels and no overview.

**Turbo Vision** is where the whole vocabulary comes from: ` [X] ` checkboxes, ` (•) ` radio buttons, disabled items dimmed rather than removed, the hardware cursor parked on the marker cell, `»item«` markers so focus survives monochrome, tilde accelerators, and the persistent `F1 Help │ F2 Save` status line. menuconfig's vocabulary is this one, one generation removed.

**gitui** models its command bar in three states rather than two - absent when unavailable, dimmed when available but not enabled in this context, normal when enabled - with an `order` field so the bar degrades predictably on a narrow terminal.

**raspi-config** is worth stealing one idea from and rejecting the rest: mnemonic ids stay stable when a conditional entry is absent, but no current value appears anywhere in a menu, so learning which audio output is selected requires opening the submenu. It is the cleanest available demonstration of nailing goal 1 and failing goal 2.

**GOV.UK's check-answers pattern** is the confirm screen: one row per question, question rephrased as a short statement, a Change affordance per row, only relevant sections shown, skipped optional answers rendered as "Not provided", and a return to the overview after each change rather than continuing forward.

## Traps

- **Do not hide questions whose `when` is false.** The list shrinks unpredictably, "how much is left" stops being answerable, and the user cannot see the state of settings they cannot see. This is menuconfig's signature support question, and nconfig's `XXX` row is the correction
- **Do not spend two rows per item.** btop's options menu is name on one row and value on the next, which yields about eleven visible options in a 32-row terminal; 23 questions becomes three screens with no overview. If a row needs two lines, the label is too long
- **Do not let colour be the only carrier of anything.** htop's segmented memory meter has open issues for low contrast in every shipped scheme and for segment boundaries being unreadable; terminal themes are user-overridden, `NO_COLOR` is honoured by Textual, and Textual's `dim` passes SGR 2 through to a terminal that may ignore it
- **Do not put help in a modal.** menuconfig's `<?>` replaces the list, so you read why a question is unavailable while unable to see it; `dialog`'s `--item-help` and Kconfiglib's `F` mode are both retrofits correcting exactly this
- **Do not overlay a `Select` popup on a full-height list.** With the cursor low in the list, the overlay covers the rows the user is comparing against
- **Do not add back-navigation late.** debconf retrofitted it into one frontend and standardised a protocol result code for it; a late addition will not be uniform across screens
- **Do not build a second tier.** Chromium's own configuration policy says "users might need to turn the feature on/off" is not sufficient justification for a permanent flag, and GNOME's removed options reappeared in gnome-tweaks and dconf-editor - an unsupported surface carrying a breakage warning. Twenty-three questions has neither the scale gap nor the support boundary that Chrome and Firefox have
- **Do not give one setting two homes.** Windows Settings and Control Panel have coexisted since 2012 with asymmetric search: searching in one returns results from the other, and searching in the other returns nothing for things that exist
- **Do not reveal a control only on focus or hover.** The sharpest Ventura complaint is popup buttons that appear only under the pointer, and reveal-on-focus is the same trap with a different trigger. There is no guaranteed mouse here at all
- **Do not de-emphasise what you want read.** Luguri & Strahilevitz's hidden-information condition - smaller, less prominent presentation of the same content - doubled acceptance from 14.8% to 30.1%. Dimming is not styling, it is hiding
- **Do not attach a confirmation step to one branch only.** Obstruction was the strongest form manipulation they tested, 16.7% to 23.6%, and it works purely through asymmetric effort. Changing an answer and keeping one must cost the same
- **Do not word a branch as an admission.** Confirmshaming moved acceptance from 14.8% to 19.6%; both branches get neutral value wording
- **Do not ship a progress bar.** Villar, Callegaro & Yang's meta-analysis found constant indicators non-significant and slightly the wrong way, slow-to-fast indicators raising dropoff odds 1.56 times, and the GDS Carer's Allowance team removed theirs with completion rates unchanged. A 23-question survey where the first few differ and the rest are accepted produces the slow-then-fast shape, which is the harmful one
- **Do not let "accept everything" be what happens when Enter is held.** Make it one named action and give the CLI an explicit flag so the expert path is honest rather than accidental
- **Do not fire the attention marker on anything you cannot defend.** The cry-wolf literature says operators match their response rate to observed reliability within a session, and the priority inference from `copier.yml` will sometimes be wrong. Say so in the docs
- **Do not cite choice overload, 7 plus or minus 2, or Hick's law to justify any decision here.** All three fail against their own primary sources and a reviewer who checks will find it in ten minutes

## The unresolved tension

The two goals conflict less than the brief assumes, and the evidence dissolves most of the conflict in one direction: goal 2 is not the price of goal 1, it is the only measured way to make goal 1 safe. Prefilling is the load reduction and it is measured - Engstrom & Sinibaldi found 63.1% and 61.6% of prefilled respondents rating the task "much less burdensome" against 29.3% of controls, with completion at 553.5 and 506.4 seconds against 628.2. Prefilling is also what produces configurations nobody chose - Madrian & Shea's auto-enrolled cohort sat at 71% on a combination 1% of self-enrolled participants selected. The mechanism that decides between those two outcomes is not motivation: Eggs & Jackle found that satisficing measures and interviewer characteristics did not predict confirming a demonstrably false preload, while measures of task difficulty did. People accept a default when checking it is expensive. That makes the dense always-visible list the evidence-backed choice rather than the aesthetic one, and it makes every column that lowers verification cost - the value, the provenance mark - load-bearing.

What the evidence does not settle is the trade at the margin, and there are four live gaps. First, no study in any domain measures total burden with defaults versus without, including the downstream cost of repairing a wrong one; anyone claiming the net goes one way is asserting. Second, nobody has tested a count line plus a marked list against a marked list alone, so the count line ships as one cheap row and not as a claim. Third, nobody has run the flat-versus-sectioned comparison with a perceived-load dependent variable, in any literature; the sections verdict above rests on the naming component being null and the spacing component carrying the effect, which is weaker than a direct test. Fourth, none of this has been measured in a terminal. Every number in this document is a transfer: the dropdown studies are mouse-and-web and one of their mechanisms, scroll-wheel mis-selection, does not exist here; Pernice & Budiu is unrefereed industry work; Cockburn's 80 ms per item was calibrated on eight graduate students.

Where the researchers contradicted each other, three disagreements matter and each has a better-supported side. On prefilling, one digest reported that prefilled respondents made *more* meaningful edits, 88-89% against 48.3%, and called it the opposite of the acquiescence prediction; reading the paper shows that figure is a rate among edits made, not a count, and the counts run the other way - 2.1 and 2.0 mean changes under prefill against 10.6 in the control. The inversion is wrong and should not be repeated. On grouping, one digest recommends sectioning the 23 rows into labelled blocks citing Couper's split-grid result; that experiment put the sub-grids on separate pages, so it is evidence for splitting the task, not for headings on one screen, and Smyth's isolation of headings from spacing is null. On choice overload, one digest lists Dean, Ravindran & Stoye as live dissent finding strong overload at small set sizes; they do, but the authors themselves say they "deliberately picked an (arguably somewhat artificial) environment", that their aim was detection methodology rather than prevalence, and every option was visible in both arms. The three adjudications read the primaries and are better supported than the digests.

Three decisions are therefore the designer's own, not lookupable. The first is the degradation order at 80x24: the evidence ranks value and provenance above alternatives and origin, but it does not price a collapsed-defaults summary line against a scrolling list with a pinned counter, and both preserve goal 2 in different currencies. The second is whether the third provenance state - the default the user looked at and kept - earns a glyph. No prior art implements it, no study measures it, and the argument for it is purely deductive: it is precisely the information that lets a user stop worrying about the other twenty-two. The third is whether to infer question priority from `copier.yml` at all. The inference is available (no default means high, `when`-gated inherits its controller, computed means derived), debconf's twenty-five years say the ranking is the thing that makes many questions feel like few, and the cry-wolf literature says a marker that fires on things that do not matter stops being read. Nothing in the evidence decides which risk is worse here.
